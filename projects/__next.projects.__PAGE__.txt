19:T1812,<h2 id="applied">Applied</h2>
<p>Five public repositories on <a href="https://github.com/mtusman-ai" rel="noopener">GitHub</a>, each installing and running end to end on a clean machine under continuous integration, with every number regenerated by the committed code. Each one leads with the decision it informs and an honest result, not the code.</p>
<h3 id="ai-build-buy-boost--a-board-level-build--buy--boost-decision-costed">ai-build-buy-boost — a board-level Build / Buy / Boost decision, costed</h3>
<p>The question a leadership team actually faces is not which forecasting model to build, but which architecture to invest in. This repository works one realistic enterprise-AI decision end to end — build in-house, buy a SaaS platform, or <em>boost</em> a platform with a proprietary feature layer — through an Architecture Decision Record, a weighted decision-driver model, a risk-adjusted NPV, and a 10,000-draw Monte Carlo sensitivity. The recommendation leads: <em>Boost</em>, with a three-year NPV of about £1.24m and an explicit falsifier that would prove it wrong. The company is fictitious and every figure is synthetic and labelled. Decision-first, not model-first.</p>
<p>→ <a href="https://github.com/mtusman-ai/ai-build-buy-boost" rel="noopener">github.com/mtusman-ai/ai-build-buy-boost</a></p>
<h3 id="sentiment-rag-service--turning-customer-text-into-a-served-signal">sentiment-rag-service — turning customer text into a served signal</h3>
<p>The question behind any "what are customers telling us" use case: can free-text feedback become a signal a system can serve and query? This builds a sentiment classifier, extends it with a retrieval-augmented (RAG) layer, and serves it behind a containerised FastAPI API with CI — the production-shaped path from raw text to a queryable signal. The served baselines score 0.768 (Naïve Bayes) and 0.834 (VADER) on the public NLTK <code>twitter_samples</code> set; the number is the evidence, not the point.</p>
<p>→ <a href="https://github.com/mtusman-ai/sentiment-rag-service" rel="noopener">github.com/mtusman-ai/sentiment-rag-service</a></p>
<h3 id="timeseries-forecasting--multi-horizon-forecasting-with-an-honest-back-test">timeseries-forecasting — multi-horizon forecasting with an honest back-test</h3>
<p>A forecast is only useful if you know when to trust it. This forecasts multi-horizon on the public ETTh1 benchmark, served behind an API with CI, and the back-test is honest about its limits: gradient-boosted forecasting leads at short horizons (1h and 6h), while simple persistence and seasonal baselines win from 12h out. The decision-relevant takeaway is the horizon beyond which a planner should fall back to a baseline.</p>
<p>→ <a href="https://github.com/mtusman-ai/timeseries-forecasting" rel="noopener">github.com/mtusman-ai/timeseries-forecasting</a></p>
<h3 id="heart-failure-clinical-ml--clinical-ml-with-leakage-handling-r">heart-failure-clinical-ml — clinical ML with leakage handling (R)</h3>
<p>A risk model is worthless if it scores well only because it quietly used information from the future. This R/tidymodels pipeline predicts mortality on the UCI Heart Failure Clinical Records set, and its real subject is data leakage: the admission-only random forest is the model I report (ROC AUC 0.730), and the follow-up-<code>time</code> model is kept only to measure the leakage it introduces, not to flatter the score. What it shows is the discipline to separate a deployable signal from an artefact.</p>
<p>→ <a href="https://github.com/mtusman-ai/heart-failure-clinical-ml" rel="noopener">github.com/mtusman-ai/heart-failure-clinical-ml</a></p>
<h3 id="heart-failure-clinical-ml-py--the-python-companion">heart-failure-clinical-ml-py — the Python companion</h3>
<p>The scikit-learn build of the same analysis, prepared as a worked example for the postgraduate Data Mining module, whose hands-on labs I deliver. Same dataset and method, rebuilt in Python; the admission-only random forest scores ROC AUC 0.817 (10-fold cross-validation mean 0.771). The figures differ from the R build because the library and the random split differ; the README explains that rather than reusing the R numbers. Together the two repositories are a paired R-and-Python proof of the same method.</p>
<p>→ <a href="https://github.com/mtusman-ai/heart-failure-clinical-ml-py" rel="noopener">github.com/mtusman-ai/heart-failure-clinical-ml-py</a></p>

<h3 id="ieuk-2025--product-roadmap-case-study-bright-network">IEUK 2025 — product-roadmap case study (Bright Network)</h3>
<p>A product-management response to Bright Network's Internship Experience UK (IEUK) 2025, Technology &#x26; Engineering set project. Acting as product manager for a wellness-app brief, I built a six-month product roadmap to raise retention and engagement and prepare a premium tier, within a team of three engineers and one designer. The work covers user research into personas, RICE and MoSCoW prioritisation, a phased roadmap with user stories and success metrics, a technology-stack rationale, OKRs, and a risk register. The case-study company (Routina) is fictional; the analysis is mine.</p>

<h2 id="seminars">Seminars</h2>
<h3 id="knowledge-graphs-for-healthcare--msc-seminar-2021">Knowledge Graphs for Healthcare — MSc seminar (2021)</h3>
<p>A seminar I gave as an MSc Computing student for the Semantic Web module: a review of biomedical ontologies and clinical knowledge graphs. It covers ontology foundations, then SNOMED CT, the Gene Ontology, and BioPortal. Two contrasting builds follow: the COVID-19 Knowledge Graph, built automatically from the research literature, and the DRANPTO dementia-agitation ontology, hand-built with clinical domain experts. The closing comparison sets out where automated and manual ontology construction each have the advantage.</p>
